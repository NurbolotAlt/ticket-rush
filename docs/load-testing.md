# Нагрузочный тест «открытие продаж»

Сценарий [loadtest/journey.js](../loadtest/journey.js): 3000 человек приходят в первые
10 секунд после открытия продаж и проходят весь путь, как живые люди — страница и
каталог, WebSocket и очередь, впуск, 2–5 с выбора мест по живой схеме зала, бронь 1–4
соседних мест (заняли — ищут другие), 1–3 с раздумий, оплата (10% кликают дважды),
PDF по уведомлению. Мест 2000 — часть людей законно получает «всё распродано».

```bash
sh loadtest/reset.sh
docker compose -f docker-compose.yml -f loadtest/docker-compose.loadtest.yml up -d --scale api=2 --scale worker=2
docker run --rm -i --network ticket-rush_default grafana/k6 run - < loadtest/journey.js
docker compose up -d --scale api=2 --scale worker=2   # вернуть обычный режим nginx
```

## Что нашёл тест и как исправлено

**Продуктовые ошибки — их видно только на полном сценарии:**

1. **Распродано, а очередь ждёт.** Все места проданы, но 1935 человек продолжали
   ждать. Теперь впускатель видит «продано всё», перестаёт впускать и сообщает
   всем ждущим; вход в очередь отвечает `409 sold_out`.
2. **Ушедшие держали пропуска.** 200 из 200 мест покупателей занимали люди, которые
   ушли (не нашли мест, закрыли вкладку), — пропуск жил 10 минут, очередь стояла.
   Теперь впущенные, как и ждущие, проверяются на присутствие (heartbeat): молчит
   минуту — пропуск отзывается.

**Производительность — по профилю, а не на глаз.** `py-spy` на воркерах API под
нагрузкой показал, что CPU уходит на рассылку по WebSocket, а не на Redis, базу или
логи:

3. **Пакетирование изменений схемы зала:** изменения за 150 мс уходят зрителю одним
   сообщением с диапазоном версий — кадров в десятки раз меньше.
4. **Без таймера на каждую отправку** (~8% CPU): медленного клиента ловит
   переполнение его очереди, у каждого клиента и так свой отправитель.
5. **Middleware request-id не оборачивает WebSocket-сообщения.**
6. **nginx: ECDSA вместо RSA-2048** (рукопожатие во много раз дешевле) и общий кэш
   TLS-сессий.
7. **Асинхронный коммит для восстановимых записей воркера.** База простаивала, а
   время уходило на `COMMIT` — ожидание сброса журнала на диск. PDF и счётчик попыток
   можно потерять при падении Postgres без вреда (их перегенерирует сверка); заказы и
   билеты коммитятся синхронно.

## Честные оговорки

- **Генератор нагрузки на той же машине.** k6 сам занимал 7–9 ядер из 12: каждый
  виртуальный пользователь, как настоящий браузер, разбирает каждое изменение схемы
  зала. В жизни это делают компьютеры пользователей. Суммарно контейнеры просили
  ~2000% CPU на 12 ядрах, поэтому хвосты (p95) — это в основном ожидание процессора.
  Сравнение «до/после» корректно (одинаковые условия), абсолютные p95 — нет: для
  них генератор запускают на отдельных машинах.
- **Пороги p95 не выдержаны** (страница < 2 с, бронь < 1 с, оплата < 2 с) — по той же
  причине. Медианы в пределах.
- **Docker Desktop под Windows**: виртуальный диск медленнее серверного SSD, что
  увеличивает время `COMMIT`.
